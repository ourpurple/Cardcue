# 解析引擎 V2：模型直解、交易明细与还款账户改造计划

更新日期：2026-09-28。

**状态：用户已授权按计划开发；以下仍是目标方案，实际进展和未验证项见文末实施记录。**

本文替代此前草案中与已确认决策冲突的设计。开发期间不擅自升级现有数据库、重解析真实邮件、调用收费模型或部署服务。

## 1. 已确认的业务决策

| 编号 | 用户确认的方案 | 实施边界 |
|---|---|---|
| 1 | 独立还款每卡一个还款账户；合并还款由同一持卡人的同银行还款账户关联多张卡 | 正式账单归属于还款账户，不依赖各卡账单日不同来避免冲突 |
| 2 | 历史数据先预览、人工确认后迁移 | 不自动拆分、合并或重新分配欠款；归属不明的旧记录保留并标记待处理 |
| 3 | 页面操作对象与显示对象一致 | 卡片行操作卡片，账户行操作账户；有历史记录优先停用／归档；合并还款卡不提供普通拆分入口 |
| 4 | 用户提供的银行分类作为默认规则，允许账户级例外 | 未知或冲突模式进入人工确认；有正式账单的账户不能直接切换模式 |
| 5 | 正文和支持的附件直接交给模型解析 | 保留 MIME 解码与安全处理；不做本地业务文本提取，不自动回退正则 |
| 6 | 交易明细本期做到提取、后台查看、确认保存 | 关联正式账单版本；暂不做消费统计和 Android 明细页面；银行还款明细不自动生成系统还款记录 |
| 7 | 可以先确认可靠的账单汇总，再补全明细 | 明细保持部分／待核对状态；金额、账户或卡片归属不确定时阻止账单确认 |
| 8 | 联动调整账户与卡片、草稿确认、账单列表与详情 | Android 不新增明细界面，但必要的数据同步和金额显示兼容纳入验收 |

### 范围外

- 消费统计、自动消费分类、提醒、真实支付及银行转账。
- 自动清理历史数据、自动合并同名持卡人的账户、自动把演示欠款上传为正式数据。
- 为实现模型直解而自动开通新供应商、购买服务或上传真实邮件进行测试。
- Android 新增交易明细页面。

## 2. 当前实现基线与主要问题

以下描述依据当前代码，而不是此前草案的假设：

1. `DraftService.parse_email_source_multi()` 优先选择首个可提取文本的 PDF 附件；否则将 HTML 正文转为纯文本，或使用纯文本正文。当前并未完整组装全部正文和附件。
2. 主流程优先调用 `ManagedExtractor`，失败由服务层回退规则；无有效模型配置也有规则路径。不是所有邮件都先执行正则再交给模型。
3. `ManagedExtractor` 按配置的输入上限检查并拒绝超限；另一 `ModelStatementExtractor` 路径存在固定 10000 字符截断。改造必须梳理两条路径及调用入口，不能只修改其中一处。
4. 当前草稿没有逐笔交易数据和明确还款模式。
5. 正式账单按 `(account_id, currency, statement_date)` 唯一识别。确认相同组合的草稿会创建账单新版本；若独立还款的不同卡误用同一账户，后确认的卡可能替代前一张卡的有效金额。
6. 管理后台已经包含两组银行和基本分卡／合并展示。主要缺口在于姓名分组不可靠、主行操作仍使用第一个账户、状态和账单归属不一致，不只是增加标签或重命名常量。

## 3. 还款账户与账单归属

### 3.1 银行默认规则

以下是用户指定的项目默认规则，不作为所有银行产品均无例外的外部政策声明。

| 模式 | 银行 | 账单及明细归属 |
|---|---|---|
| 独立还款 `per_card` | 农行、建行、中行、中信、邮储、工行、交行、兴业、广发 | 每张卡的独立还款账户；账单及明细识别到卡 |
| 合并还款 `consolidated` | 浦发、华夏、招商、民生 | 持卡人的银行还款账户；交易保留有依据的卡片信息 |
| 待确认 | 未配置银行、无法确定账户模式、规则与邮件证据冲突 | 不默认拆分或合并，人工确认后再正式入账 |

- 后台维护规范银行标识、别名及默认模式；前端和模型输入使用同一规则来源。
- 账户保存已确认的模式、来源（银行默认／人工例外）和修订信息。
- 模型可报告识别模式和证据，但不能自行覆盖账户配置。银行默认、账户例外和邮件证据不一致时产生明确冲突。
- 未知模式使用空值并显示“还款模式待确认”，不得默认采用 `per_card`。

### 3.2 数据归属与唯一性

**独立还款**：一个 Account 代表一张卡的独立还款单元。现有多卡混存账户必须经人工确认整理后才能用于新的独立账单确认。账户无卡时可作为待完善占位，但不得作为已完整匹配的独立卡账单账户。

**合并还款**：一个 Account 代表同一持卡人在该银行的一个已确认还款单元，可以关联多张卡。不同账户不能仅凭姓名相同自动合并。

- 保留正式账单 `(account_id, currency, statement_date)` 唯一身份方向；独立卡通过不同 account_id 隔离，同日同币种不会互相覆盖。
- 确认前后台校验卡片所属账户、账户模式、状态及匹配证据。不能只保存草稿 `matched_card_id` 而不约束正式账单归属。
- 有效草稿粒度：独立还款为“卡片 × 币种 × 账期”；合并还款为“还款账户 × 币种 × 账期”。
- 同一封邮件可以返回多张卡、多种币种或多个账期的草稿。统一输出 `statements` 列表，不再把“一封邮件一个草稿”作为合并还款约束。
- 尾号不是唯一键；姓名、银行简称、发件人也不能单独决定账户身份。使用稳定账户／卡片 ID 和已确认的持卡人关联。
- 不同币种分别保存与汇总；合并账户同一账单只统计一次，不按名下卡片数量复制欠款。
- 同账户同币种同账期再次出现时，区分重复来源和真正的账单更正，不自动把任意新草稿当成更正版。

### 3.3 历史数据保护

- 先生成预览：原账户及卡片、拟调整的归属、关联账单／版本／还款记录数量、冲突及无法确定的记录。
- 用户确认后才执行可追踪、可重试且幂等的迁移；记录旧 ID 到新归属的映射和操作审计。
- 模式新增字段通过明确数据库迁移加入；旧账户未完成核对时不能被自动认定为已整理。
- 归属明确且获确认的历史账单可整体调整归属，保留版本和还款链路；归属不明的保留原账户，不拆分金额、不复制还款、不强行合并。
- 页面分组不是数据库合并。历史多个账户可在已确认关联下分组展示，但要标明底层账户，不自动改变正式数据。
- 迁移前备份，验证恢复路径；执行时校验修订号和冲突，避免与确认、还款、归属变更并发产生不一致。
- 已有正式账单的账户变更模式必须走预览与确认流程；不允许普通编辑直接切换。

## 4. 模型直解与可靠性边界

### 4.1 输入方式

```text
邮件原始数据
  → MIME 解码／正文与附件拆分
  → 内容清单与安全处理（保留来源、结构和附件关系）
  → 模型能力及输入／输出预算检查
  → HTML／纯文本正文＋支持的 PDF／图片附件直接提交模型
  → 结构校验＋证据校验＋后台还款模式与归属校验
  → 账单草稿＋交易明细草稿＋完整性状态
  → 人工核对
      ├─ 汇总可靠：确认正式账单及可确认明细
      └─ 明细不完整：保留待核对状态，之后补全，不新增重复欠款
```

- MIME 解码、附件解码、内容类型判断不属于业务字段文本提取，继续保留。
- HTML 不转换为纯文本模型输入；保留表格、表头、行列合并关系和账单文字。去除可执行内容、事件及外部加载行为，不盲目删除可能承载账单内容的节点。
- 纯文本正文直接提供；正文、全部附件均建立清单，不再仅选择第一个可读 PDF。
- PDF／图片交给支持相应输入的供应商适配器；先验证当前模型配置能力，不能假设现有接口接受文件。
- 加密附件、损坏附件、不支持的内容、模型缺失配置或额度不足明确标记待处理。不得静默忽略附件后宣称整封邮件完整解析。
- 正文和附件重复出现的同一账单／交易保留多来源证据，不重复记账。
- 不自动加载远程图片、链接或跟随邮件指令；邮件、附件、元数据和模型输出均是不可信数据。

### 4.2 失败、超限及重试

- 新正式解析流程不自动调用旧 HTML 正则或 PDF 本地文本提取路径；旧模块可暂保留用于历史回归，但不能作为 V2 隐式回退。
- 记录待配置、待重试、不支持附件、需密码、超限、部分解析等可解释状态。
- 网络或供应商暂时异常采用有界重试；无配置、不支持类型、需密码等条件未改变时不盲目重试。
- 检查输入和输出预算、终止原因及 JSON 完整性；禁止静默截断输入、交易列表或模型输出。
- 超限内容可以按完整表格／页面分段，保留表头、账户、币种、账期和来源上下文；无法可靠分段时转人工处理。
- 缓存键包含源内容及附件指纹、模型配置版本、提示词／合约／清洗版本、有效模式与规则修订；模式或来源改变时不能误用旧结果。
- 重解析新增可追踪解析批次；不覆盖已确认版本。重复任务和重复确认在数据库事务中幂等处理。
- 日志只记录安全状态、耗时、计数和用量，不记录密钥、完整卡号、原始邮件或模型原文。

### 4.3 证据与字段校验

- 金额使用整数最小货币单位，拒绝浮点数和布尔值；缺失金额不是 0。
- 日期、卡尾号、账户标识、币种、交易类别缺失时保留未知；缺年份不能简单根据邮件日期猜补。
- HTML 证据支持限定的空白／实体归一化和单元格定位，但不使用语义模糊相似度代替证据。证据校验不是重新用纯文本做业务提取。
- PDF／图片证据保留附件 ID、页码及可定位区域／摘录；定位及金额关系不可核实时标记待人工核对。
- 不默认表格永远比正文可靠；来源冲突保留证据并要求核对。
- 非账单邮件可以返回无账单结果；缺关键字段时保留待核对草稿，不制造金额或交易。

## 5. 交易明细与确认保存

### 5.1 数据字段

拟扩展契约如下，具体命名在开发时与 API 统一：

| 层级 | 主要字段及约束 |
|---|---|
| 账单草稿 | 还款模式、银行／持卡人线索、账户与卡片候选、币种、账期、账单日／还款日、汇总金额、证据、冲突原因、解析批次 |
| 交易草稿 | 来源行标识、交易／入账日期、原始描述、商户（有明确依据时）、交易类型、整数金额与币种、原币金额与币种（如有）、可空卡尾号／待确认 card_id、逐字段证据及异常原因 |
| 明细完整性 | `complete`／`partial`／`not_provided`／`failed`／`unknown`，识别行数、有效行数、异常行数、预期行数（仅有依据时）、未处理来源及原因 |
| 正式明细 | 稳定 ID、归属账户／可空卡片 ID、关联账单版本、来源与解析批次、确认信息、明细集版本和完整性状态 |

- 卡尾号未知时允许为空，不能为满足“每笔标卡”而猜测；独立还款草稿确认必须已解决所属卡片／账户身份。
- 消费、退款、还款、费用、利息、分期、调整、撤销、未知类型分开标识；金额方向有明确证据才归一化，不把所有“撤销”一律造为负交易。
- 类别本期只保留邮件中明确给出的值，不自动推断消费分类。
- 明细合计不能直接替代账单应还金额；只有核对公式所需项目完整时才进行对应对账。
- 异常行不能静默丢弃，保留受保护的来源位置及错误原因供核对；不在日志中保存原始行。
- 不以“日期＋金额＋商户”作为唯一去重条件，避免误删同日同金额的真实多笔交易。优先使用来源行身份、银行交易标识及人工核对。

### 5.2 确认与后续补全

- 后台允许查看逐笔明细及证据，并核对／修正归属、字段和异常。
- 本期采用正式交易持久化方案，不止在草稿 JSON 中留存。草稿数据与正式数据分离，正式交易可按账单版本查询。
- 汇总金额、日期、币种、模式和账户／卡片归属可靠且经用户确认后，可以确认正式账单。
- 明细完整时，可随账单核对确认并保存；部分明细经明确核对可保存为部分明细集，其他条目保留待核对，不将整个明细集标为完整。
- 后续补全生成新的可追踪明细集版本，关联原正式账单版本，不重复创建账单或欠款，不修改已确认明细快照。
- 账单金额本身发生更正时走现有账单版本机制，重新核对明细关联，不把纯明细补全当作金额更正。
- 邮件内银行还款交易只是交易数据，不自动创建、撤销或修改系统 Payment；记录还款不代表发起银行转账。
- 正式明细来源不能因删除草稿而失去依据；有确认关联的草稿默认归档／保留必要来源引用，不级联删除正式数据。

## 6. 管理后台联动

### 6.1 账户与卡片

| 场景 | 展示 | 操作与状态 |
|---|---|---|
| 独立还款 | 每卡独立一行，显示银行、持卡人、卡尾号和“独立还款”标签 | 编辑／停用该卡；账户操作另设明确入口，不影响其他卡 |
| 合并还款 | 每个已确认持卡人还款账户一行，显示关联多卡，可展开 | 主行编辑／归档该账户；子行单独编辑／停用卡片 |
| 历史多账户待整理 | 明确标注底层账户及待整理状态 | 选择具体操作对象，不使用第一个账户充当整个分组 |
| 身份或模式不明 | 独立保留，显示“待确认”，无卡账户显示待完善 | 不因空姓名、同名或相同尾号自动合并 |

- 合并展示基于稳定身份与已确认关联，而不是 `(银行简称, 姓名)` 字符串拼接。
- 模式、规则来源由后台返回，前端仅负责格式化；重命名 `MULTI_ACCOUNT_BANKS` 等不是本期核心交付。
- 状态分别显示卡片状态、账户状态；历史分组有混合状态时明确显示，不沿用第一项状态。
- 有历史账单、正式明细或审计关联的卡片／账户优先停用或归档；无历史记录时才允许通过后台校验后的明确删除。
- 合并还款卡不提供普通“拆成独立账户”按钮；确需变更走账户归属预览和确认。后台也需拒绝绕过页面的无效操作。
- 绑定新卡明确目标账户；独立还款新增另一张卡时建立其独立还款账户，不能绑定进已有独立卡账户造成混存。
- 提示文案限定为“同一还款账户、同一账期、同一币种汇总一次”，不写“该银行所有卡只需还一次”。
- 分页和计数区分卡片数、还款账户数和展示行数。

### 6.2 草稿确认

- 独立还款只匹配具体卡片及其独立账户；合并还款匹配还款账户，具体消费卡作为明细信息。
- 模式未知、身份多候选或证据冲突必须解决后才能确认；不能只高亮推荐而继续允许错误归属。
- 展示来源证据、完整性、未处理附件和异常明细；账单确认与明细确认状态分别可见。
- 支持“先确认账单、后补全明细”，确认按钮明确此次保存的范围。

### 6.3 账单列表与详情

- 独立账单显示具体卡；合并账单显示持卡人还款账户及关联卡片，不伪装成其中一张卡的账单。
- 列表金额只按正式账单计数，不按展开卡片重复计数；不同币种分别汇总。
- 详情提供账单版本、还款记录、明细列表、来源、异常状态和后续补全入口。
- 停用或归档不抹去历史归属，旧账单仍能追溯。

## 8. 验收标准

以下为必须覆盖的场景；未通过的项目不能标记为已完成。

| 场景 | 预期结果 |
|---|---|
| 同银行同持卡人两张独立卡，同账单日、同币种 | 两个还款账户、两份账单，金额分别有效，无版本互相覆盖 |
| 合并账户多卡，同账期同币种 | 一份正式账单，多卡明细归入该账户，欠款计一次 |
| 同邮件含不同币种／多个账期 | 按正确粒度拆分，不跨币种或跨期合并 |
| 空姓名、同名持卡人、相同卡尾号 | 不自动合并或错误匹配；有歧义时待确认 |
| 账户模式人工例外、未知银行、邮件证据冲突 | 前后端采用同一规则；未知／冲突阻止错误确认 |
| 独立卡行编辑、停用、删除 | 只作用于明确对象，不波及兄弟卡及其账单 |
| 合并主行／子行操作与历史多账户分组 | 明确账户／卡片对象，不默认操作第一个账户；混合状态不隐藏 |
| 有历史记录的删除或合并卡普通拆分请求 | 后台保护记录，提供归档或受控变更流程 |
| 迁移中断、重试、并发操作、恢复 | 不重复迁移，金额及版本／还款链路不丢失；歧义记录原样保留 |
| HTML 表格、PDF、图片及正文＋多附件 | 模型直接接收支持的内容，所有来源可追踪；重复来源不重复记账 |
| 模型不可用、超限、加密／不支持附件、输出截断 | 显示可解释失败／部分状态，不回退正则，不伪装完整成功 |
| 超过原 500 条限制、异常行、跨段表头 | 不静默截断；有效／异常数量可核对，未处理部分明确提示 |
| 同日同金额同商户的两笔真实交易 | 保留两笔，不按弱特征误去重 |
| 金额缺失、浮点或布尔值、日期／卡号缺失 | 缺失保留未知，拒绝无效金额，不猜测 |
| 汇总可靠但明细不完整 | 明确确认账单，明细保持部分／待核对；不掩盖错误 |
| 后补明细、重复任务、重复确认、重新解析 | 不重复欠款／交易，不覆盖已确认快照，可追踪版本 |
| 邮件包含银行还款交易 | 不自动产生或撤销系统 Payment |
| 归档／删除草稿、账单更正 | 已确认明细和来源仍可追溯；历史版本不被覆盖 |
| Android 同步及金额显示 | 新归属和迁移结果正确同步；不清除旧演示记录，不重复汇总 |

质量评价：覆盖用户指定的全部银行默认模式及例外规则测试；有样本的银行逐一核对汇总字段、交易行数量和归属，缺少样本的明确标注未验证。Mock 只能证明程序行为，不替代真实模型解析质量验证。

## 10. 风险与控制

- **历史归属错误**：迁移必须预览、确认、备份和核对；身份不明不自动处理。
- **模型能力与费用**：文件输入能力和上下文限制随配置不同；开发时核实所用供应商接口，不预设通用支持或固定成本倍数。
- **完整性不可证明**：没有交易总笔数或完整附件时，不能仅凭模型声称标为完整；保存覆盖状态和待核对项。
- **操作误伤**：页面文案、请求对象、后台校验三层保持一致，不仅隐藏按钮。
- **重复入账与并发**：解析批次、来源身份、确认请求、明细集版本及数据库约束共同保证幂等。
- **安全与隐私**：输入安全处理不能替代不可信边界和人工确认；不向日志或 Git 写入原始邮件、真实账单、完整卡号及凭证。
- **兼容与回滚**：保留历史数据，明确服务端与 Room 迁移；后台测试不能替代设备验收。

- 已补充 P0-03 的只读历史归属预览：逐账户展示原账户与卡片 ID、修订、账单／版本／还款／已确认明细／关联草稿数量、同银行同持卡人其他底层账户提示、缺失卡片外键和重复尾号等风险。归属目标留空，不能由银行默认模式、姓名或卡尾号推断。管理后台可从“账户与卡片”查看，预览不写入数据库。
- 已增加逐账单显式映射预检：管理后台手动选择目标账户及独立还款卡片；后台核验来源账单全集、当前版本、账户修订、银行／持卡人一致性、目标模式／唯一卡和同账期冲突。预检始终只读，`valid_mapping` 也不代表可执行；普通拆卡或删除卡片遇到账单／草稿会阻断并提示归档／受控整理。
- 历史归属逐账单映射只读预检又加固：目标账户必须有效，独立还款目标需唯一有效卡及准确卡片 ID（归档兄弟卡不计入），多尾号已确认明细不得整体指向独立单卡；当前版本若不在账单版本清单或预览中原归属不一致亦阻断。一般人工复核提示仍非自动执行许可；管理后台目标选择禁用归档账户、只列有效卡。预检持续返回 `can_execute=false`，没有迁移写入口；真实并发和异常数据仍需隔离数据库验证。
- 已补充账户／卡片普通操作的保守边界：有正式账单或关联草稿时禁止直接改账户银行、持卡人、引用标识及还款模式；有关联草稿的账户不得直接删除；有账单或账户／卡片匹配草稿时卡片不得直接改尾号或删除。独立还款账户恢复第二张有效卡会被拒绝，新增卡与恢复卡通过账户行锁串行校验。普通拆卡只处理有效账户中的有效卡，成功拆卡同时推进旧账户和卡片修订并记录变更。这些保护不能代替历史迁移预检与执行事务。
- 已补账单人工更正的明细保留：新版本复制当前已确认交易及原来源关联，不覆盖旧版本；总额变化或旧覆盖计数不可信时不继续宣称明细完整。更正写入独立版本变更日志；草稿确认遇已有账单时锁定该账单以串行检查版本。尚无明细后补全专用流程。
- 已新增明细后补专用后端流程（迁移 `0012`，未在用户库执行）：独立明细集与逐笔快照表，已有账单版本下的旧正式明细按兼容读取；后补请求校验账单版本、明细修订、草稿修订、银行／账户／卡片／账期／币种／金额及来源，锁定账单和草稿；支持追加（保守标记部分）或显式全量替换，只有来源和预期笔数核对齐全才标记完整。请求幂等、旧快照保留，账单详情与历史快照查询可回溯；金额更正继承当前生效明细并在总额变化时降级。管理后台已接入后补入口、候选／指定草稿加载、逐笔核对、追加／全量替换、来源预期笔数和历史快照只读查看；后补追加时旧明细与新草稿的来源必须可核验，缺失时阻断追加并要求显式替换；后补锁顺序与普通草稿确认统一为草稿先于账单（并发效果尚待 PostgreSQL 验证）；隔离 PostgreSQL 迁移／并发验证和浏览器端到端核对尚未完成，不能勾选 P2-05 整项验收。
