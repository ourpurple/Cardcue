## 二、需要优先处理的缺口

### 1. 附件目前是"明确拒绝"，还不是"交给模型解析"

识别到 PDF／图片后提示缺少文件适配能力并阻止解析，避免了静默遗漏，但未达到文件直传目标。

### 2. 历史账户整理只有预览，没有执行功能

已有逐账单映射和冲突预检，始终返回 `can_execute=false`。备份、确认、事务执行、审计和恢复尚未形成完整流程。

### 3. 异常交易可以被阻止确认，但不能完整修正

部分结构错误会导致整次解析失败；已入草稿的异常交易在页面上不能勾选，目前也没有逐笔字段修正及重新校验流程。

### 4. 重解析批次与明细后补尚未打通

同一邮件已有草稿时会复用既有结果或阻止再次解析。独立解析批次追踪不足，影响"先确认账单后重新解析补明细"场景。

### 5. Android 升级后可能无法及时获得新增账户字段

Room 2→3 迁移只增加字段并保留原同步游标；若服务器没有新变更，客户端不一定重新获取完整快照，新增字段可能持续为空。

## 三、开发任务

### 范围

- **包含：** 完成原 Plan2 未完成能力，修复 Android 兼容缺口，补齐数据库、Web、Android 和解析质量验收。
- **不包含：** 新增 Android 交易明细页面、自动消费分类、真实支付；不自动合并同名持卡人，不按卡尾号认定唯一身份，不自动拆分历史欠款。

### 任务列表

- [ ] **N1｜建立可复现的验证基线**
  - 固定测试环境，建立隔离 PostgreSQL 测试库。
  - 先验证现有迁移链，再为后续改动持续增加迁移测试；同时覆盖旧数据、演示数据和备份恢复。
  - **验收：** 空库升级、旧版本库升级和恢复均可重复执行；无需修改用户数据库。
  - [x] 远程专用 `cardcue_v2_test` 中空库和 0007 合成历史库升级至 0012，迁移后无遗留测试 schema。
  - [x] 隔离 Android 包的 Room 1→2／2→3、演示行保留及缓存失败保护用例首轮通过（全套设备测试尚有失败）。
  - [ ] 对演示数据的服务端隔离补齐设备／联调断言，并完成失败项复测；先查清原包状态。
  - [ ] 建立第二隔离恢复库，完成非空合成账单的 `pg_dump`／`pg_restore` 演练与关联金额核对。

- [ ] **N2｜修复 Android 升级后的缓存刷新**
  - 增加缓存协议版本或一次性完整同步标记，不依赖服务器恰好产生新事件。
  - 同步失败时保留旧缓存，下次重试；离线仍只读，不清除本地数据。
  - **验收：** 旧 App 升级后，即使后端零变更，也能获得账户模式、持卡人和修订信息；刷新过程原子完成。

- [ ] **N3｜补齐账户身份和模式边界**
  - 明确持卡人稳定关联方式，验证账户级例外优先于银行默认规则。
  - 覆盖同名持卡人、同尾号不同卡、不同币种、未知模式以及独立／合并还款场景。
  - **验收：** 不误合并账户；独立还款按卡展示，合并还款在已明确归属的账户内展示多卡，欠款只统计一次。

- [ ] **N4｜实现模型文件直传**
  - 先接通一个明确支持目标文件类型的供应商适配，再扩展其他适配。
  - 将配置测试与正式解析统一，验证 PDF、图片和正文混合输入。
  - 对加密、不支持、超限、部分来源失败给出明确状态；不能可靠分段时转人工，不本地提取后冒充文件直传。
  - **验收：** 使用合成文件完成实际能力验证；任何未处理来源都可见，不能误标记为完整解析。

- [ ] **N5｜补齐解析批次、来源追踪与幂等**
  - 增加可追踪的重解析批次，允许同一邮件产生新的待审核结果，不覆盖已确认依据。
  - 完善缓存版本维度、数据库并发去重、正文与附件重复来源处理及证据定位。
  - 正常区分"非账单""解析失败"和"部分解析"。
  - **验收：** 并发任务不重复入账；同日同额真实交易不被误删；原邮件重解析可以用于明细后补。

- [ ] **N6｜完成异常明细人工处理流程**
  - 保留异常行的受保护来源引用和原因，不因单行错误无差别丢弃可用结果。
  - 增加逐笔修正、归属调整、重新校验和修订冲突处理，并保留修改记录。
  - **验收：** "查看异常→修正→重新校验→确认／后补→查询历史"完整可用；未解决异常不能伪装成完整明细。

- [ ] **N7｜完成历史归属受控迁移**
  - 在现有预览和映射预检基础上，增加明确确认和执行入口。
  - 执行前备份，事务内重新校验版本、锁定相关记录，保证幂等和审计。
  - **验收：** 在隔离库验证重复提交、并发修改、执行失败及恢复；保留账单版本、还款记录和明细依据，归属不明时拒绝执行。

- [ ] **N8｜完成 Web、数据库与 Android 联合验收**
  - Web 覆盖账户管理、草稿修正、确认入账、明细后补及历史查询。
  - PostgreSQL 覆盖重复确认、后补与更正并发、迁移一致性和事务回滚。
  - Android 覆盖 Room 升级、离线只读、在线写入与同步并发、账户展示和金额统计。
  - **验收：** 形成可重复执行的自动化用例和设备测试记录；构建成功不代替业务验收。

- [ ] **N9｜建立解析质量基线并准备分批启用**
  - 按银行、还款模式、来源类型和异常场景建立合成／充分脱敏样本集。
  - 分别记录字段准确率、交易行召回率、归属正确性、完整性误判、耗时和费用；没有样本的银行明确标为未验证。
  - 更新 README、总计划、架构及验证记录，消除过期说明。
  - **验收：** 先确定质量门槛，再评估是否达到；验证非破坏性恢复方案后，经授权分批启用，不自动退回旧规则解析。

## 四、执行顺序与完成标准

建议顺序：**N1 → N2 → N3 → N4 → N5 → N6 → N7 → N8 → N9**。每项开发时同步补测试，不把所有验证留到最后。

每项分别记录：

1. **代码实现完成**
2. **自动化验证通过**
3. **集成／设备验收通过**

只有满足该项全部验收要求才勾选完成，避免继续出现"代码做了很多，但计划无法判断进度"的情况。

## 五、需要用户配合的事项

1. **模型文件能力测试（N4）：** 确定供应商／模型，并授权必要的外部调用和费用；无需在聊天中提供密钥。
2. **质量与设备验收（N8/N9）：** 提供或确认可使用的充分脱敏样本，以及可用的 Android 手机／模拟器。
3. **真实环境操作（N9）：** 真实邮件外发、用户数据库迁移和部署启用分别取得授权；前面的本地开发和合成测试不必因此停住。
